# AI 调参与性能档案

本文记录引擎「为什么这么写」。调棋力前必读——每一条都对应线上真人对局暴露的问题。

## 1. 难度旋钮（ai.ts 顶部）

```ts
easy:   { maxDepth: 3, timeLimitMs: 500 }
medium: { maxDepth: 4, timeLimitMs: 1500 }
hard:   { maxDepth: 6, timeLimitMs: 2500 }
```

- **改弱 easy 只能降 `maxDepth`**（比如 2）。不要恢复「在次优着法里随机主动送分」：`EASY_SLACK = 0` 是刻意为之，棋力靠深度天然变弱，而不是故意输。旧实现按吃子价值排序随机，实测中局 29% 概率白送炮。
- 时限是硬保护：迭代加深超时即用已完整搜完的最深层结果，低配机自动降级；2 核服务器建议不超过 2500ms，并发调用时上游还要加自己的超时锁。
- 残局加深只放宽**深度上限**（≤12 子 +6 / ≤18 子 +4 / ≤24 子 +2），时间预算不放松；easy 不参与，保证新手能赢。

## 2. 评估函数

红方视角正分 = Σ（子力价值 + 位置表分 × 兵种系数 × 阶段系数） + 威胁修正

- 子力：仕/士 120、相/象 120、马 400、炮 450、车 900、兵 200（帅 0）
- 位置表（PST）7 张 10×9 表在 ai.ts 内，**按红方真实行号编写**：行 0 = 黑底线（兵推进最远处），行 9 = 红底线。索引函数 `viewRow = 红 r / 黑 9-r`、`viewCol = 红 c / 黑 8-c`。
  - ⚠️ 历史事故：镜像写反成「红 9-r」后，红兵每进一步自评 -120 分 → AI 全程不推兵；红帅位置项恒 0；大车赖在家里。外部观感就是「AI 乱走」。改表后跑自对弈确认双方行为对称。
- 阶段：≤20 子 PST 权重 ×0.8；≤12 子 ×0.5 且兵 +120（残局底兵/助攻升值）
- 威胁修正（≤24 子才算，省开局性能）：被敌攻击且无己保护的子罚 25% 子力分。攻击图是伪合法纯扫描版（attackMap），比 legalMoves 快 5-10 倍，威胁评估不需要王安全精度。

## 3. 开局行为（重灾区，谨慎动）

AI 选着顺序：**开局库棋谱 → 开局常识候选池 → 常规搜索**。

1. **棋谱优先**：该局面棋谱分支 ≥3 手时，等概率随机选一手棋谱（不按权重！权重只是棋谱次序）。
2. **分支不足**（《橘中秘》是单主变棋谱，92.7% 局面只有唯一着法）：仅在前 2 回合，用「全部合法着法 + 开局常识修正分」构造候选池，depth 2 浅搜索打分，只剔除明显亏的（安全阈值 150 ≈ 3/4 兵），再按**棋子类型配额**（炮/车/相 ≤1、马/兵 ≤2、仕 0、帅 0）等概率随机。
3. 所有根节点候选在开局阶段（≥30 子且 ≤10 回合）都要过**亏本兑换拦截**（`isLosingCaptureInOpening`）：用大子吃有保护的小子必拦（近似 SEE：落点走后是否被攻击）。
4. 反空挪子：走后形成第 2 次重复局面的着法扣 50 分（第 3 次由判和覆盖）。

事故背景：玩家反馈「开局频繁瞎走炮、重复乱走」。根因有三层——① 单主变棋谱等概率随机退化；② 炮合法着法天然是马的 5-6 倍，随机池被炮占满（42%）；③ 旧炮位置表鼓励炮无脑前拱。修复靠「类型配额 + 常识修正分 + 修 PST」，**不要**靠收紧择优阈值（曾把阈值写成 40，结果马卒相全被挤掉，池里只剩炮）。

## 4. 搜索性能清单（按收益排序）

| 优化 | 做法 | 收益/教训 |
|------|------|-----------|
| 棋盘扁平编码 | `Uint8Array(90)` 数字编码，克隆 = `slice()` | 比双层对象数组快 5-10 倍 |
| legalMoves 单克隆 | 所有伪走法共用一个棋盘走/回退 | 每节点 40+ 走法不重复分配 |
| 搜索跳终局判定 | `applyMove(..., {skipStatus:true})`，将死由「无合法走法」分支识别 | 最大单点开销，提速 2-3 倍；quiescence 内补被将无着法检测 |
| Zobrist 哈希 | 两张 32 位表组合 52 位安全整数当 TT 键 | 比字符串拼接快 11.7 倍（0.16µs vs 1.75µs/节点），同预算多搜一层 |
| 置换表 + PV 优先 | 上次迭代/TT 最佳着法排首位 | 开阔中局时限内多搜一层；最可能好的着法排最后是 alpha-beta 大忌 |
| killer + MVV-LVA | 同级剪枝着法优先，吃子按 价值×10−小子价值 | 常规有效 |
| PVS + null-move | 首着满窗，后续零窗验证失败再重搜；depth≥3 且 >4 子时让手 | 标准剪枝 |
| quiescence | 叶节点只延伸吃子（≤6 层）+ stand-pat | 消除水平裁剪，防白送子 |
| 偏移表提常量 | 马/士/象/车的步长数组放模块级 | 最热函数 GC 归零，movegen +25% |
| 超时批量检查 | 每 2048 节点查一次 `Date.now()` | 检查成本可忽略 |

TT 容量 `1<<18`（约 26MB），在 2G 内存服务器上安全；不要回到百万级字符串键（约 300 字节/条，是 OOM 元凶）。

## 5. 绝杀分与置换表校正（极易复发的事故）

绝杀分编码为 `INF - ply`（距根节点步数），让引擎天然偏好**更快的杀法**。但该值依赖 ply，而 TT 按局面存取、同一局面会在不同 ply 命中——直接存读会把「2 步杀」当「6 步杀」，引擎会偏好慢杀甚至为虚假快杀送大子。入表必须 `toTT(score,ply)` 剥掉 ply、出表 `fromTT` 加回；`|score| ≥ INF-1000` 视为绝杀分段。

## 6. 开局库数据说明

- 数据来自明代古谱《橘中秘》（生产库还混入了 depth≤2 全展开浅层索引，本包已剔除：浅层数据 29 手里 24 手炮、0 手马，不合格）。
- 镜像展开是功能不是优化：棋谱全是右路开局，玩家走左路对称开局（炮八平五）时，没有镜像就 0% 命中。
- 库着法仍逐条过 `legalMoves`，脏数据回退搜索，永不进对局。
- 想换/扩库：按 `{k: 'r'+90字符, m:[{f,t,w} ...]}` 追加即可，w≥500 会被当作棋谱档；改动后跑 selfcheck 的开局库断言。

## 7. 验证改动

```bash
node scripts/selfcheck.mjs
```

任何引擎/评估/库改动后必须：23 项断言全过 + AI 自对弈能正常终局。建议再手动下两盘：一盘验开局多样性（连开三局 AI 第一手不应雷同到只剩炮），一盘验残局（大子兑完后不降级乱走）。
